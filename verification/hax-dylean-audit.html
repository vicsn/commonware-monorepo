Auditing the Merkle inclusion proof

Eight steps for checking that the Hax → DyLean proof of Merkle inclusion says what the report claims about the Rust that production runs. Wherever one piece of code must agree with another, both are shown side by side with what links them.

The proof lives on branch verify/qmdb-hax-dylean, in the checkout that holds this page. The report states its results; this guide is for the person who checks them. It is written for a reader who knows Rust and Merkle trees and has not used Lean or DyLean. No step asks you to read a proof.

Production baseline: b45ef2d78ea7535d8a51588912ba1e13e461b146. The panels and tables marked as generated are built from the sources by verification/audit/build.py, and check.sh fails when they are stale.

Out of scope: the hax pipeline. This audit assumes that hax, Charon and Aeneas translate the Rust faithfully into Lean, and that their models of the Rust core library match Rust. It does not audit them. Step 4 only checks how the pipeline is used: which tools are pinned, that regenerating the Lean reproduces the committed files, and that nothing was filled in by hand. A translation bug that changes the meaning of the verifier would leave every theorem here true of the wrong program.

Scope and assumptions

In scope: the Merkle target of the Hax → DyLean experiment. That is the production files it shares with the proof, the verification-only client, the handwritten Lean that states what the Rust means, the application assumption, the protocol model, the theorem statements and the checks that a machine runs. The leaf target is used as a warm-up. The BLS target is out of scope; it shares steps 4 to 7.

Four things are assumed and not audited. For each, the audit still checks how the proof depends on it.

#Assumed, not auditedWhat the audit still checksStep
A1hax, Charon and Aeneas translate the Rust faithfully. Their models of the Rust core library match Rust: integer overflow, a shift that is too large and an index out of bounds are failures.The tool pins and where the binaries come from. Regenerating the Lean is byte-identical. Assumptions/FunsExternal.lean declares nothing.4, 7
A2Lean’s kernel and its three standard axioms (propext, Classical.choice, Quot.sound).The axiom audit covers every theorem, and it fails when an escape hatch is planted.7
A3DyLean’s core: traces, what the attacker knows, reachability and its tactics.Its pin, the patch applied to it, the three #combine blocks that define what statements mean, and the two actions accept and receive.6
A4The hash function itself.Nothing. The byte-level theorems hold for any hash and return an explicit collision, so no property of the hash is used.1

A theorem about generated Lean says something about production only if every link below holds. Each step of the audit discharges named links, and each side-by-side panel carries a label that says how strong its link is today.

The labels: proved a named Lean lemma states the link and Lean checks it. tested a test samples it. trusted a person must read both sides; nothing checks it. assumed one of A1 to A4. same code one side calls or includes the other. no link the two sides should agree and nothing relates them.

Order. Start step 7 first and let it run: it builds the toolchain and takes the longest. Then work through steps 0 to 6 in order. Steps 3, 5 and 6 are where a person’s judgement matters most. The times are rough and add up to about a day.

The leaf target proves a deliberately small property through the same route as Merkle: a client holds a trusted digest of one item and accepts only that item. Reading it first shows every kind of artefact once.

What a statement can depend on

A statement means what the definitions it mentions mean. The probe Closure.lean follows every definition that the cited statements mention, through definitions and never through proofs. The handwritten Lean it reaches is the Lean that a person must read. Every row is shown in a panel of this guide.

Four statements that the report cites are not restated in SecurityTheorems.lean: verify_total, honest_opening and extra_sibling_rejected in Verifier.lean, and client_step_sound in Symbolic.lean. The table shows the first three; read the fourth as the per-step form of the trace theorem.

terms.rs (80 lines) and traversal.rs (165 lines) in full. Then the changes to hasher.rs Diff and proof.rs Diff against the baseline.
Pass when

Links
L0, L1.
Time
1.5 hours.

The proof needed production to be split. Hash inputs moved into terms.rs, as lists of parts over an abstract hash. The recursive traversal moved into traversal.rs, behind three small traits. Production reaches both through thin wrappers. The change is 444 added and 28 removed lines in four files.

The crate that hax extracts includes the two files by path, so L1 holds by construction: lib.rs has one #[path] line for each. What a person checks is that neither file has a use of its surroundings, which would resolve differently in the two crates.

The regression test covers both tree families and both bagging policies, every range of trees with 1 to 16 leaves, with and without node collection, and three kinds of damaged input. It compares one peak at a time.

Diff compares this checkout’s file against the original baseline b45ef2d78, including test changes in the same file. New files have an empty left pane. Install the local VS Code handler with python3 verification/qmdb/code-diff.py --install.

The theorems are about qmdb::verify and qmdb::client_step. Production never calls either. They are a second verifier, written for the proof, that calls the shared traversal and the shared encodings with one item, one peak and a trusted tree size. So the theorems reach production’s Proof::verify_element_inclusion only as far as the two verifiers return the same verdict, and that is shown by tests.

This step does not establish that the translation is right. That is assumption A1. Its purpose is to let you recognise the generated code that the statements in steps 1, 5 and 6 mention, and to notice a gross mismatch.

Lean does not reason about the generated code directly. The proofs first show that each generated encoding function returns the hash of one named input. From there on, statements talk about those inputs.

Residual risks

What remains after every step passes. Each is a property of the approach or a gap that the first pass confirmed. None is a flaw in a proof.

#RiskLinkWhat would close it
R1The translation from Rust to Lean is wrong in a way that changes what the verifier means.L3An audit of hax, Charon, Aeneas and their library models, or a second extraction route that agrees.
R2The proved verifier is not the deployed one. It is a second verifier for one item of a tree with one peak and a trusted size. Tests on trees of up to 64 leaves tie it to production’s verifier.L2Extract production’s own reconstruct_root_inner, or prove the client equal to it.
R3The modelled root is not QMDB’s. The client hashes the forward-fold domain byte and QMDB folds backwards, so the client accepts no opening under a root built with QMDB’s hasher.L2Give the client QMDB’s domain byte and build the test trees with qmdb::hasher(). The proofs do not depend on the byte.
R4The tree size is trusted. Production reads leaves and inactive_peaks from the proof, which the attacker writes, and relies on the root committing to them. No statement covers that, and the tests never vary them.L2A statement in which the size comes from the proof and the root alone is trusted.
R5The byte-level reading of production’s hasher is a person’s reading of ByteTerms and of two doc comments. No test or extraction touches it.L4Extract ByteTerms::hash over an abstract byte hasher.
R6Honest roots are built by code that the proof does not see. The tree builder hashes nodes through a second encoding, and the journal chooses what is stored at each location.L5Route the builder through the part lists of terms.rs; state the snapshot in terms of the journal.
R7The trace theorems could hold for the empty reason. Nothing shows that the client logs an event on any reachable trace.L6A theorem that some reachable trace logs an honest opening.
R8The trace theorems are about a symbolic model: terms keep the boundaries between hashed parts, an item is always a literal, and the hash is a function on terms. The byte-level theorems say nothing about traces.L6Inherent to the symbolic approach. Read the two families of statements together.
R9The toolchain is pinned by name, not by content: the hax binary and the dependency builds are whatever is on the machine, and no CI runs the check.L8Record how the binary is built, hash it, and run check.sh in CI.
