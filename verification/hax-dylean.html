Merkle inclusion and BLS signer attribution with DyLean

What does successful verification authenticate? For a historical QMDB Merkle proof, it is the item at a particular location in a trusted snapshot. For a BLS signature, it is an earlier signing of the claimed message and domain by each claimed, uncompromised signer.

The Hax → DyLean experiment extracts production Rust with hax and places the extracted checks in DyLean protocol traces. For each target, Lean proves what an accepting party has authenticated on every reachable trace, against an attacker who controls the network. It lives on branch verify/qmdb-hax-dylean, in the checkout that holds this page. Other approaches that we tried are listed at the bottom.

What is proved, assumed and validated

Merkle. Fix a valid historical commit, a trusted root and a location in an unpruned, power-of-two MMR with ForwardFold and zero inactive peaks. The adversary chooses the item and siblings. The production entry point is Proof::verify_element_inclusion.

BLS. The symbolic claim covers a single signature, several signers on one message, or one signer on several messages. For each claimed signer, compromise is evaluated at acceptance. The registry and its proof-of-possession (PoP) policy are part of the premises.

TargetChecked guarantee
Merkle inclusionFor any hash, two openings that the extracted production verifier accepts at one location under one root carry the same item, or a checked finder returns two different hash inputs with the same digest. The verifier is total and accepts honest openings. With DyLean’s collision-free hash, every reachable acceptance by the extracted client identifies the trusted snapshot height, an in-range location and the stored item, for any root under which the stored items have accepted openings. Such roots exist at every height up to 62.
BLS signer attributionEvery reachable acceptance yields a strictly earlier matching signing event. An honest aggregate can reach acceptance from a prefix containing its signing events.

Assumptions and trust boundaries

Merkle · From an accepted opening to the stored item

  • Snapshot: the application supplies the trusted root and height of a fixed historical snapshot, and every stored item has an opening that the production verifier accepts under that root. honest_snapshots_exist shows that such roots exist at every height up to 62. Proof construction, pruning, recovery and concurrent mutation remain outside the theorem.
  • Hashing: a hash is any function of the encoded parts of its input. Production’s ByteTerms is read as hashing the concatenated bytes, with fixed-length, injective digest bytes. The byte-level theorem reduces conflicting openings to an explicit collision without a probability bound. The trace theorem assumes DyLean’s collision-free hash and concatenation constructors. SHA-256 is not proved.
  • Extracted scope: there are no callback contracts. The extraction includes the production opening backend, with its element and sibling streams, and the production hash-input encodings; the encoding must keep inputs of one kind apart, which Lean proves for concatenated bytes and for DyLean’s constructors. The client supplies the MMR child positions, the single-peak layout and the outer checks.
  • Outside the proof: the production Hasher/Family wrappers, their bounds checks and blueprint, hashers that override the default encodings (grafting), node collection, multiple peaks and multi-item ranges, and the journal and storage. Differential tests compare the client with Proof::verify_element_inclusion.
  • Checking machinery: DyLean network reachability, attacker knowledge and event invariants; the shared symbolic reading that maps the Rust terms and messages onto DyLean constructors; hax/Charon/Aeneas extraction and library models; Lean’s kernel and standard axioms.
  • Meaning: byte equality requires codec injectivity to imply decoded-operation equality. Log inclusion does not establish current activity or the latest value.

BLS · From a valid aggregate to an identity

The registry binds the protected identity to its canonical key and excludes aliases. Every admitted key needs a derivable PoP for that exact key in a separate signing context. Applicants may propose related keys and add, subtract, scale or replay signature terms. Under these rules another admitted key has zero contribution at the protected signer’s coordinate, which rules out rogue-key attribution. The symbolic threat model draws on Hofmeier et al.

The algebra uses formal integer coefficients. Applying the result to BLS12-381 requires valid group elements, distinct message and PoP tags, unambiguous domain framing, correct hashing and pairing, and cached aggregates that represent the claimed lists. The same-message verifier delegates PoP validation to its caller. A computational reduction and production admission proof remain open.

Merkle collision finder and cost

The DyLean finder is a Lean function, not a replay. For each opening it lists the hash inputs from the root’s down to the leaf’s, and it returns the first corresponding pair that differs and has one digest. Lean proves that an accepting run of the extracted verifier hashes exactly those inputs. The theorem holds for any hash; with production’s concatenated bytes the pair is two byte strings. Its executed check uses a hash with one digest and recovers a leaf witness only. Finder and proof Diff · executed check Diff

For a conflicting accepted pair at height h, each opening requires one positioned leaf hash, h ordered parent hashes and one wrapped-root hash. The finder examines at most h + 2 paired hash sites. With 32-byte digests and 8-byte positions, each opening hashes its item length + 8 bytes at the leaf, 72h bytes at parents and the prefix length + 32 bytes at the wrapper. This structural bound covers the number and sizes of hash inputs. A computational advantage bound still requires a security game.

The DyLean finder follows the reduction in DyLean’s own Merkle example. The collision argument also follows the F* Merkle tutorial and VCVio’s pinned binding proof.

Production changes

Merkle. The DyLean branch changes four production files (+365/−28 lines outside their test modules, and 79 test lines in proof.rs). hasher/terms.rs lists the parts of every hash input once, and the default Hasher methods hash through it, so production digests are unchanged. traversal.rs holds the single production recursion and the opening backend that proof.rs previously defined. The extraction crate includes both files unchanged.

BLS. No production lines changed. The imported Hax harness copies the verifier bodies with abstract primitive types.

Subtree::reconstruct_digest delegates every range, with or without node collection, to traversal.rs. The core consumes an outside-subtree sibling, hashes an in-range leaf, or recurses left then right and records both children before hashing their parent. traversal::Opening owns the iterator, sibling cursor and collector, and proof.rs supplies only typed positions and the hasher through FamilyNodes.

The production traversal uses subtree width; FamilyNodes uses ilog2() for family geometry. A test-only reference traversal serves as a regression oracle.

No public API, wire/storage format, allocation strategy or production dependency changed. Runtime performance has not been benchmarked.

Other experiments. We also tried these routes; this report does not describe them.

  • Hax → Aeneas → Lean (verify/qmdb-hax-lean): an executable collision finder over the extracted shared Merkle traversal, and BLS signer attribution over six extracted verifier and hashing functions, whose extraction the DyLean BLS proof imports.
  • Verus (verify/qmdb-verus): the production traversal body refines a stateful range model with a collision finder; BLS attribution is proved over a handwritten model without a correspondence proof to the Rust verifier.
  • Charon → Aeneas → Lean (verify/qmdb-aeneas): selected-leaf binding of the shared general traversal, reduced to a byte-level collision.
  • Earlier Charon → Aeneas → Lean (verify/qmdb-hax-legacy-lean): subtree binding of a single-item production core up to a byte-level collision, and the journal’s single-item range checks.
