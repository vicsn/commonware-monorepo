Writing the DyLean specification in Rust

In Cryspen's SHA-3 proof, the trusted text is Rust. There is a pedantic spec crate, ensures contracts that compare the implementation with it, and hax extraction of both into Lean. Reviewers read the Rust, and Lean checks about 15,700 lines of proof. On this branch it is the other way round. hax extracts one function, reconstruct. The spec it is proved against is 90 lines of handwritten Lean: encodings, replay, the outer check, the client and the events. This page compares four ways to move that spec into Rust, by how much a person still has to read and trust.

The options

Five setups, from today's Lean model to an all-Rust protocol

DyLean proves statements about a symbolic term algebra, where hash, concat and literal are free constructors, and about the Traceful trace monad. Rust computes on bytes and hax extracts into RustM. So a Rust spec helps DyLean only if Lean can plug the symbolic constructors into it. Options A to C make the spec generic over a Terms trait, which matches DyLean's own HasExecBytes style and the extracted Backend trait. Option D binds concrete functions to Lean models instead.

What changes

Today versus option B: the spec moves into the Rust lane

Migration

Are we implementing DyLean in Rust?

Mostly no. Options A, B and D move QMDB's own logic into Rust: encodings, replay, the single-item check and, from B on, the client decision. Attacker knowledge, traces, reachability, event invariants and #combine stay in Lean under every option, because Rust has no counterpart for them. The only DyLean-facing piece in A and B is a three-method Terms trait. It is a seam, not an implementation. Rust tests implement it with SHA-256 and byte concatenation, and Lean implements it with DyLean's constructors. Option C is the exception. Its Net trait copies DyLean's receiveMessage and logEvent into Rust, and a new Lean adapter has to map that copy back onto DyLean.

One-time migration audit

This is what someone reviews once to accept the switch. The trusted text left afterwards is covered in the next section. The cheap route keeps today's audited Lean (Model.lean, the symbolic backend and the client) as the reference until Lean proves the extracted Rust equal to it. Code covered by such a proof only needs reading for intent. The new equivalence and security statements need careful reading. Code with no audited counterpart must be audited from scratch.

If the differential tests show that today's Lean model disagrees with production, for example on the root wrap encoding, then the migration has found an existing gap. Fix the reference first, then prove equivalence against it.

After migration

Trusted text left per option

Each bar adds up the trusted text a reviewer must read and judge once the migration is done, split by kind. Effort points weight each line by how hard it is to check. A Rust spec line counts 1: it runs, and differential tests compare it with production. A handwritten Lean definition or theorem statement counts 2. A Lean model of Rust or DyLean semantics counts 3. DyLean configuration counts 0.5. The thin rule under each bar shows the range of the estimates. Proofs, generated extraction and test harnesses are left out, because Lean, pinned comparison or execution checks them.

Where each piece lives

How each part of the spec is checked

The rows are the pieces the authentication theorem depends on. "Tested" means the Rust spec is run against Proof::verify_element_inclusion with SHA-256 on random trees. That samples production behaviour. It does not extend the theorem to production hashing, which stays outside the formal boundary in every option.

Recurring cost

What a change costs to re-audit

One-time line counts miss the main difference. Today the hash encodings in Model.lean sit outside the extracted traversal, so if production changes one, nothing fails. With a Rust spec, the differential test fails before anyone has to notice.

Not audited

New Lean proof to write

Proof is effort, but no reviewer has to read it. All options keep today's 236 lines of proof (replay_eq, verify_iff, Binding.lean, client_preserves). A, B and D add the equivalence between the extracted spec and Model.lean, plus no-overflow lemmas for u64 arithmetic. C also needs monotonicity and refinement lemmas for the Traceful adapter.

Cryspen's theorem is a functional ensures, which Rust can express. A DyLean theorem quantifies over reachable traces and attacker knowledge, and Rust has no counterpart for those. So the DyLean configuration and compat patch (42 lines), the theorem statements (20), and the snapshot, reachability config and event invariant (8) stay in Lean. Option B's other 26 Lean lines are the DyTerms instance, the client wrapper and an estimate for hax core-model gaps.

Method

How the numbers were made

  • Measured: non-blank lines in verification/qmdb/dylean/ at 6fe467206, sorted by role. The traversal is storage/src/merkle/proof/traversal.rs at 5b7e44f63, 55 lines, and it is reviewed as production code in every option. Not counted: 236 lines of proof, 107 lines of generated extraction, 40 lines of sanity checks and 102 lines of runner scripts.
  • Estimated: the size of new code in options A to D, from the sketches above, with low and high bounds. The widest range is hax core-model gaps (0 to 25 lines), such as u64::to_be_bytes or slice get, if the Lean core models lack them. Cryspen hit the same issue.
  • Migration estimates assume today's Lean stays as the reference until the equivalence proofs pass. The sizes of tests and runner changes are estimated from the existing check-bridge.sh and validate.py.
  • Weights are a judgement, not a measurement. With every weight set to 1 the chart shows raw lines.
  • hax 0.5 constraints: it rejects specs on trait declarations, so contracts use the _requires_x and _ensures_x function pattern from hax's own examples/sha3. Putting spec and traversal in one crate (via #[path]) avoids the missing multi-crate extraction.
  • Toolchains: DyLean pins Lean 4.36.0-rc1, while hax 0.5 uses 4.35.0. Every option keeps lean435.patch until those versions align.
  • Out of scope: the BLS experiment in verification/bls has the same split, with its routing algebra in Lean. It is not estimated here.
  • Source: Cryspen, SHA-3 with hax 0.4. DyLean pin 2254f7d; hax checkout at version 0.5.0.
