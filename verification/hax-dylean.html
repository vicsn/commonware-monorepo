Merkle inclusion and BLS certificates with DyLean

What does successful verification authenticate? For a historical QMDB Merkle proof, it is the item at a particular location in a trusted snapshot. For a BLS multisignature certificate, it is a quorum of flagged committee members, each of whom signed the verifier’s namespace and message earlier if it registered its own key and is uncompromised.

The Hax → DyLean experiment extracts production Rust with hax and places the extracted checks in DyLean protocol traces. For each target, Lean proves what an accepting party has authenticated on every reachable trace, against an attacker who chooses what that party receives. It lives on branch verify/qmdb-hax-dylean, in the checkout that holds this page. Other approaches that we tried are listed at the bottom.

What is proved, assumed and validated

Merkle. Fix a valid historical commit, a trusted root and a location in an unpruned, power-of-two MMR with ForwardFold and zero inactive peaks. The adversary chooses the item and siblings. The production entry point is Proof::verify_element_inclusion.

BLS. Fix a committee, given as its registered public keys in member order. The adversary chooses the namespace, the message, the signer flags and the signature of a multisignature certificate. The production entry point is Generic::verify_certificate, which runs the checks in rules::verify_certificate. The extracted client applies them with the N3f1 quorum. Threshold certificates share the seam. Aggregates of one signer over several messages are outside this target.

Merkle inclusionFor any hash, two openings that the extracted production verifier accepts at one location under one root carry the same item and the same siblings, or a checked finder returns two different hash inputs with the same digest. The verifier is total and accepts honest openings. For any hash on DyLean terms, every opening that the extracted client logs on a reachable trace identifies the trusted snapshot height and an in-range location, and its item is the stored one or the finder returns a collision between the logged opening and the snapshot’s. With DyLean’s collision-free hash the logged item is the stored one, and an accepted opening is the only one at its location under its root. The snapshot supplies a root and an accepted opening for each stored item; such snapshots exist for every hash at every height up to 62.
BLS certificatesFor any signature scheme, the extracted client step returns a verdict on every certificate. It accepts exactly when the flags span the committee, at least the N3f1 quorum of members is flagged, the signature decodes, and the signature verifies for the hash of the given namespace and message under the sum of the keys registered at the flagged indices, each once and in index order. Two certificates accepted over one committee flag more common members than the committee tolerates as faulty. In the linear attacker model, for any registered keys and any hash, every certificate that the extracted client logs on a reachable trace flags a quorum, and each flagged member that registered its own key and was not compromised before the acceptance signed exactly that namespace and message strictly earlier, or the hash collides between an input that the member’s secret was applied to and either the subject or the possession input of a flagged key. With a collision-free hash the signing event exists, and two logged certificates share a member that signed both subjects when no more members are faulty than the committee tolerates. A certificate that a quorum signed can be accepted.

How is production code connected?Production’s multisignature and threshold schemes call rules.rs, which states the checks over abstract keys, points, committees, signer flags and lazily decoded signatures and has no imports. Hax extracts that file unchanged, with a client that supplies the N3f1 quorum. Lean proves what each rule accepts by induction over the extracted loops, with no reference model. The client logs the event returned by the extracted client_step with the subject and flags it was given.
Are termination and arithmetic safety proved?For every committee of fewer than 264 members, all signer flags and every signature, the extracted client step returns a verdict without panic or divergence. It rejects an empty committee, for which production’s quorum panics. Production’s quorum also panics above 232 − 1 members, where the client computes the same formula.
What about attestations?rules::verify_attestation accepts exactly when the signer index is a member, the signature decodes and it verifies under that member’s key for the subject (verify_attestation_iff). Batch verification of attestations and certificate assembly are outside the extraction.
What about threshold certificates?The threshold verifier calls rules::verify_identity. It accepts exactly when the signature decodes and verifies under the group key for the hash of the given namespace and message (verify_identity_iff), which is subject and domain binding. Leaf · The smallest target, for auditing the route

The leaf target proves a deliberately simple property through the same files as Merkle and BLS, so the shared setup can be read on its own. The only production code involved is terms::leaf_digest, which the default production hasher calls for a leaf. A 41-line client step parses the received message, hashes it with that function at position 0 and compares the digest with a trusted commitment. Lean proves that the extracted step accepts exactly the committed item, and the shared client action turns that into the trace theorem. It uses the ideal hash only, so it has no collision alternative.

An auditor reads the client step, the commitment assumption, and the client, event invariant and theorem statement in the protocol module. The checked module needs no review: the trace proof uses one fact from it. Assumptions and trust boundaries

Merkle · From an accepted opening to the stored item

  • Snapshot: the application supplies the trusted root and height of a fixed historical snapshot and, for every stored item, the siblings of an opening that the production verifier accepts under that root. The snapshot fixes its hash, which may be any function on DyLean terms. honest_snapshots_exist shows that such roots and siblings exist for every hash at every height up to 62. Proof construction, pruning, recovery and concurrent mutation remain outside the theorem.
  • Hashing: a hash is any function of the encoded parts of its input. Production’s ByteTerms is read as hashing the concatenated bytes, with fixed-length, injective digest bytes. The byte-level theorem reduces conflicting openings to an explicit collision without a probability bound. The trace theorem holds for any hash on DyLean terms and carries the same explicit collision as its alternative; it assumes DyLean’s concatenation constructors. With DyLean’s hash constructor no collision exists. SHA-256 is not proved.
  • Extracted scope: there are no callback contracts. The extraction includes the production opening backend, with its element and sibling streams, and the production hash-input encodings; the encoding must keep inputs of one kind apart, which Lean proves for concatenated bytes and for DyLean’s concatenation under any hash. The client supplies the MMR child positions, the single-peak layout and the outer checks.
  • Outside the proof: the production Hasher/Family wrappers, their bounds checks and blueprint, hashers that override the default encodings (grafting), node collection, multiple peaks and multi-item ranges, and the journal and storage. Differential tests compare the client with Proof::verify_element_inclusion.
  • Checking machinery: DyLean network reachability, attacker knowledge and event invariants; the shared symbolic reading that maps the Rust terms and messages onto DyLean constructors; hax/Charon/Aeneas extraction and library models; Lean’s kernel and standard axioms.
  • Meaning: byte equality requires codec injectivity to imply decoded-operation equality. Log inclusion does not establish current activity or the latest value.

BLS · From an accepted certificate to its signers

  • Committee and registration: the application supplies the registered keys in member order. They may be any keys, including rogue ones and keys that sum to zero. The trace theorem protects a member whose registered key is its own, and it requires a derivable proof of possession (PoP) for every flagged key of a submitted certificate. Production does not check PoPs, so registration must. rogue_key_accepted shows what the premise prevents: without it, a certificate is accepted for an honest member that never signed.
  • Signature scheme: the abstractions follow Hofmeier et al. The code-level theorems hold for any hash and check functions, as in the paper’s validation models, where verification is an arbitrary function. The trace theorems use a linear model in the style of its attack-finding models. A key is an integer combination of member secrets, a signature is an integer combination of hashed inputs under those secrets, and verification compares the signature with the sum of the flagged keys applied to the hashed subject. The attacker starts from what honest members signed, every member’s PoP for its own key and anything under a compromised secret, and it adds and scales. Recombination, rogue keys and splitting zero are all expressible.
  • Hash: any function of an input that is either a namespace with a message or a key whose possession is proved. The two kinds are different inputs, which stands for distinct message and PoP domain tags, and the namespace and message are separate arguments, which stands for production’s length-prefixed framing. The collision alternative is explicit, and with an injective hash it is absent. Hashing to the curve is not proved.
  • Extracted scope: rules.rs is extracted unchanged. Lean reads its committee, signer flags and lazily decoded signature as lists and an optional point. The client supplies the N3f1 quorum, which a test compares with production for every committee size up to 100,000.
  • Outside the proof: the production adapters for the pairing, the participant map, the signer bitmap and lazy decoding; decoding and group checks; hashing to the curve and the pairing; signing, batch verification of attestations and certificate assembly; the consensus wrappers that choose namespaces and subjects. Differential tests compare the client with Generic::verify_certificate on both variants. Applying the result to BLS12-381 also needs a computational reduction, which remains open.
  • Checking machinery: DyLean reachability and event invariants over signing, compromise and client events. This model has no network: what the attacker may submit is the precondition of the client’s transition. The rest is shared with Merkle: hax/Charon/Aeneas extraction and library models, Lean’s kernel and standard axioms.
  • Meaning: the theorem attributes a signature to each protected flagged member. It says nothing about flagged members that are compromised or registered another key, and it does not show that a member signed only one subject. Compromise is evaluated at acceptance, so a later compromise does not weaken the result.

BLS · Four further properties and what they need

None of the four is proved. The table records what the current development shows about each and the refactor or model change it would take.

Exact signer-set bindingOne signature verifies under one set of flags.False over all members, and PoP does not help. splitting_zero proves one signature accepted under five flags and under seven when two registered keys sum to zero; whoever holds one of the two secrets can prove possession of both keys. It holds on honest members: PoP gives every other flagged key zero weight on an honest secret, so two flag sets that verify one signature agree on every member that registered its own key and is uncompromised.The honest-member version needs no refactor, only a short extension of attribution in the linear model. The verifier makes one check under the group key and never sees who took part. It is a property of the scheme and its setup.The verify_identity seam exists. On top of it, either a stated attacker rule in the style of Cremers, Peltonen and Zhao, where a group signature is derivable only from a quorum of partial signatures or of compromised shares, or a derivation from Shamir sharing over a field, which needs polynomial interpolation from Mathlib; the current model uses integer coefficients and no Mathlib. Merkle collision finder and cost

The DyLean finder is a Lean function, not a replay. For each opening it lists the hash inputs from the root’s down to the leaf’s, and it returns the first corresponding pair that differs and has one digest. Lean proves that an accepting run of the extracted verifier hashes exactly those inputs and reads every sibling. The theorem holds for any hash; with production’s concatenated bytes the pair is two byte strings. On a trace, the two openings are the one that the client logged and the one that the snapshot supplies. Executed checks recover a leaf witness under a hash with one digest and, when only a sibling differs, a node witness under a hash that tells leaves apart but not nodes. Finder and proof Diff · executed checks Diff

For a conflicting accepted pair at height h, each opening requires one positioned leaf hash, h ordered parent hashes and one wrapped-root hash. The finder examines at most h + 2 paired hash sites. With 32-byte digests and 8-byte positions, each opening hashes its item length + 8 bytes at the leaf, 72h bytes at parents and the prefix length + 32 bytes at the wrapper. This structural bound covers the number and sizes of hash inputs. A computational advantage bound still requires a security game.

The DyLean finder follows the reduction in DyLean’s own Merkle example. The collision argument also follows the F* Merkle tutorial and VCVio’s pinned binding proof.

Production changes

Merkle. The DyLean branch changes four production files (+365/−28 lines outside their test modules, and 79 test lines in proof.rs). hasher/terms.rs lists the parts of every hash input once, and the default Hasher methods hash through it, so production digests are unchanged. traversal.rs holds the single production recursion and the opening backend that proof.rs previously defined. The extraction crate includes both files unchanged.

Subtree::reconstruct_digest delegates every range, with or without node collection, to traversal.rs. The core consumes an outside-subtree sibling, hashes an in-range leaf, or recurses left then right and records both children before hashing their parent. traversal::Opening owns the iterator, sibling cursor and collector, and proof.rs supplies only typed positions and the hasher through FamilyNodes.

The production traversal uses subtree width; FamilyNodes uses ilog2() for family geometry. A test-only reference traversal serves as a regression oracle.

BLS. The branch changes five production files in the cryptography crate (+296/−49 lines outside their test modules, and 4 test lines in multisig/mod.rs). certificate/rules.rs states the certificate, attestation and single-key checks once over abstract keys and points. The multisignature and threshold schemes call it through adapters and reach the same hashing and pairing calls as before, so verdicts are unchanged. The extraction crate includes rules.rs unchanged.

Two differences deserve review. Flagged signers are counted by a loop over the bitmap, where the previous code used its population count. The subject’s namespace and message are computed before the length and quorum checks, where the previous code computed them after, so a certificate rejected by those checks now pays for them.

For both targets, no public API, wire/storage format, allocation strategy or production dependency changed. Runtime performance has not been benchmarked.
